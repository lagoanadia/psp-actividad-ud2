Actividad 1.1 · start() frente a run()

Captura · salidas de la terminal con start() y con run()
4 · Diferencia entre start() y run() citando las dos salidas

Con start() hay dos hilos trabajando a la vez.

  • La salida sale entrelazada: main va por 1, hilo-trabajador va por 1, main va por 2…
  • start() pone en marcha el hilo-trabajador, que ejecuta la tarea mientras main ejecuta la suya con tarea.run().
  • Por eso unas líneas dicen hilo-trabajador y otras main: cada hilo que ejecuta la tarea imprime su propio nombre.

Con run() solo trabaja main.

  • Todas las líneas dicen main y salen seguidas, sin mezclarse: main va por 1, 2, 3, dos veces.
  • run() no crea ningún hilo. Es una llamada a un método normal, y la ejecuta quien la escribe: main.
  • El hilo-trabajador se ha creado, pero nunca se ha arrancado. Por eso join() vuelve al momento y el mensaje main: el trabajador ha terminado no es cierto.

Conclusión: start() crea un hilo nuevo que ejecuta la tarea en paralelo; run() solo ejecuta la tarea en el hilo que ya está corriendo.

12 · ¿Cuál arranca antes, el reparto entre procesos o entre hilos? ¿Cuál escala mejor?

Arranca antes el reparto entre hilos. Crear un hilo es barato porque vive dentro del mismo proceso y comparte su memoria; un proceso tiene que arrancar una JVM nueva. Se ve con N=1: 25.938 ms con hilos frente a 28.010 ms con procesos.

Escalan mejor los hilos: con 4 mejoran 2,91x (procesos 2,62x) y con 8 mejoran 3,62x (procesos 2,65x, prácticamente igual que con 4, porque 8 JVM compiten por 4 núcleos y la memoria). Pero los hilos dan un total incorrecto (con 8 faltan 7.305 primos), así que de momento son más rápidos dando un resultado que está mal.

13 · ¿Por qué el trozo 0 termina siempre mucho antes que el último?

Porque los trozos tienen la misma cantidad de números, pero no el mismo trabajo. esPrimo(x) prueba divisores hasta la raíz de x: con los números pequeños del trozo 0 termina enseguida, y con los números grandes del último trozo (cerca de 20.000.000) tiene que probar muchos más. Repartir el rango en partes iguales no reparte la carga por igual: el trozo 0 acaba pronto y su núcleo se queda sin nada que hacer, mientras el último sigue trabajando, y es ese trozo el que marca el tiempo total.

18 · Operaciones que no llevan hilo: qué se ganaría y por qué no compensa

Comprobar si una franja está libre

  • Qué se ganaría: nada. Es leer una posición de memoria y acaba al instante.
  • Por qué no compensa: crear y arrancar un hilo cuesta mucho más que la propia lectura, y habría que esperarlo con join() para saber la respuesta.
  • Además: otro hilo más tocando franja[] agrava la carrera de la sección crítica.

Formatear la fecha de una reserva para la pantalla

  • Qué se ganaría: nada. Tarda microsegundos y no espera a nada.
  • Por qué no compensa: el hilo tardaría más en crearse que la operación en hacerse.
  • Además: la pantalla necesita el resultado ya, así que habría que esperarlo igual.

5 · ¿Por qué salen distintos? Los tres pasos de n++

Salen distintos porque contador++ no es una sola operación, son tres pasos:

  1. Leer el valor de contador.
  2. Sumar 1 a ese valor.
  3. Escribir el resultado en contador.

Los dos hilos ejecutan estos pasos a la vez y pueden mezclarse: si los dos leen el mismo valor antes de que el otro escriba, los dos escriben el mismo resultado y se pierde un incremento. Cuántas veces pasa depende de cómo reparta el sistema operativo el procesador entre los hilos, que cambia en cada ejecución. Por eso cada vez se pierden incrementos distintos y el número final es diferente.

Con varios hilos, todos hacen total++ sobre la misma variable compartida, y cuando dos leen el mismo valor a la vez, uno de los incrementos se pisa. Cuantos más hilos, más veces coinciden y más primos se pierden.

13 · Conclusión con esos dos números

El fallo está en los dos casos. El yield() no lo crea: solo ensancha el hueco entre comprobar y actuar, y por eso con él salen más dobles. Sin yield el hueco sigue existiendo, es más estrecho, pero aun así se confirmaron dos reservas 647 veces de 1000. Que sea menos probable no significa que no pase: con mil usuarios reservando de verdad, un fallo poco probable acaba pasando seguro.

19 · La sección crítica del club

Estado compartido: los arrays franja[] (quién ocupa cada franja) y caduca[] (cuándo caduca cada reserva). Son static: una sola copia para todos los hilos.

Métodos que lo tocan: reservar, cancelar, limpiar e informeDelDia.

Qué pasa si dos hilos entran a la vez: en reservar, los dos comprueban franja[id] == null antes de que ninguno escriba, los dos ven la franja libre y los dos reservan. Dos usuarios reciben «Reserva confirmada» para el mismo barco. No sale ningún error.

Los tres números que lo demuestran:

  • Contador: 1.572.517 · 1.373.856 · 1.742.444 · 1.378.968 · 1.807.670 (esperado 2.000.000).
  • Primos perdidos: 2.172 con 2 hilos, 6.452 con 4 y 7.305 con 8.
  • Reservas dobles: 898 de 1000 con yield, 647 de 1000 sin él.

1 a 4 · Código: los cuatro métodos de reserva (A, B, C y el de get + put)
private static final Object CERROJO = new Object();
static final AtomicReference<String> franja = new AtomicReference<>();
static final ConcurrentHashMap<Integer,String> mapa = new ConcurrentHashMap<>();

// Versión A · bloqueo
static void reservarA(String quien) {
    synchronized(CERROJO)
    {
        if (usuario == null) { // 1 · comprobar
            Thread.yield(); // 2 · la ventana, ensanchada a propósito
            usuario = quien; // 3 · actuar
            confirmadas++;
        }
    }
}

// Versión B · atómica
static void reservarB(String quien) {
    if(franja.compareAndSet(null, quien))
    {
        confirmadas++;
    }
}

// Versión C · colección concurrente
static void reservarC(String quien) {
    if(mapa.putIfAbsent(1, quien)==null)
    {
        confirmadas++;
    }
}

// La que parece correcta y no lo es: get + put
static void reservarMal(String quien) {
    if (mapa.get(1) == null)
    {
        Thread.yield();
        mapa.put(1, quien);
        confirmadas++;
    }
}
